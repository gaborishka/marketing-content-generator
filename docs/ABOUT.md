# MarketGen AI

## Inspiration

Marketing teams face a combinatorial nightmare. Every campaign needs content tailored to specific channels, audiences, and formats. A single product launch targeting 3 channels and 4 audience segments already demands:

$$C = |\text{channels}| \times |\text{audiences}| \times |\text{formats}|$$

For a modest campaign with 5 channels, 4 audiences, and 3 formats, that's **60 unique content pieces** — each needing brand-consistent copy, compliant messaging, and matching visuals. Most teams either cut corners (reusing the same copy everywhere) or burn weeks on manual production.

We built MarketGen AI to collapse that $O(n^3)$ workload into a single campaign brief. One click, and an AI pipeline generates compliant, channel-optimized content for every combination — then lays it all out on an infinite canvas where marketers can review, edit, and approve.

## What it does

MarketGen AI takes a campaign brief — product details, target audiences, channels, compliance rules — and generates a full set of marketing content:

- **Multi-channel copy** — tailored headlines, body text, and CTAs for each channel × audience combination
- **Compliance checking** — every piece is evaluated against brand rules and regulatory constraints, with automatic revision of failed content
- **AI-generated images** — visual assets generated by Gemini, matched to each content piece
- **Video storyboards** — scene-by-scene storyboards that can be turned into Veo-generated video
- **Infinite canvas workspace** — all generated content appears as draggable cards on a spatial canvas with pan, zoom, multi-select, and connection lines between related pieces

The system supports both product-focused campaigns (linked to a product catalog) and brand/idea campaigns with freeform briefs.

## How we built it

**Frontend:** React 19 with TypeScript, using a flat file structure with all state managed through `useState` hooks in a single `App.tsx` root. The infinite canvas uses SVG for connection lines and ref-based drag tracking for smooth 60fps interaction. Tailwind CSS handles styling.

**Backend:** Firebase Cloud Functions (v2) with 5 exported functions. The Gemini API key is managed server-side via `defineSecret` — it never touches the client bundle.

**The core of the system is a multi-agent pipeline:**

```
Campaign Brief
     │
     ▼
 ┌─────────┐     Firestore reads:
 │ Planner  │───► campaign, products, compliance rules, existing content
 └────┬─────┘
      │  PlannerContext (minimal, focused)
      ▼
 ┌───────────┐    Gemini Flash (structured JSON output)
 │ Generator │───► one content doc per channel × audience combination
 └────┬──────┘
      │  ContentDoc[]
      ▼
 ┌────────────┐   Evaluator-Optimizer loop
 │ Compliance │───► score each item against rules, $s \geq 80$ to pass
 └────┬───────┘    retry budget: $r \leq 2$ attempts
      │
      ▼
 ┌───────────────┐  Parallel Gemini image generation
 │ Asset Manager │───► only runs if $T_{\text{remaining}} \geq 120s$
 └───────────────┘
```

**Orchestrator** — a deterministic code controller (no LLM routing). It manages the pipeline lifecycle, passes typed results between agents, tracks a timeout budget, and writes real-time progress updates to Firestore. The frontend subscribes via `onSnapshot` for live progress streaming.

**Trigger/Processor split** — `generateCampaignContent` (30s onCall) creates a job doc and returns `{ jobId }` instantly. `processGenerationJob` (540s Firestore trigger) picks it up and runs the full pipeline. This lets the user get an immediate response while heavy processing happens asynchronously.

**Compliance loop** — follows the evaluator-optimizer pattern. A separate Gemini call evaluates each content piece against brand rules. Items scoring below the threshold get regenerated with the compliance feedback injected as context:

$$s_i < 80 \implies \text{regenerate with feedback, up to } r = 2 \text{ retries}$$

**Timeout budgeting** — the pipeline runs under a hard 540s Cloud Functions limit. A `TimeoutBudget` class tracks elapsed time with a 30s safety margin:

$$T_{\text{remaining}} = T_{\text{max}} - T_{\text{elapsed}} - T_{\text{margin}}$$

Image generation is skipped entirely if $T_{\text{remaining}} < 120s$. At every stage, an expired budget triggers graceful degradation — we accept what we have rather than crash.

## Challenges we ran into

### Multi-Agent Pipeline Orchestration

The hardest part wasn't any single agent — it was making them work together reliably under time pressure.

The compliance retry loop was deceptively tricky. Failed items need regeneration, but only the failed items should be re-checked on the next pass. We track a working set of `docsToCheck` that narrows on each iteration, avoiding redundant API calls for already-passing content.

Timeout budgeting required thinking about every stage as potentially the last. The orchestrator checks `budget.isExpired()` before each stage and between retry iterations. If time runs out mid-compliance, we accept partial results. If the asset manager doesn't have enough runway, we skip it entirely. Every path through the pipeline produces a valid (if incomplete) result.

Error isolation was critical. A single failing compliance check shouldn't abort the entire batch. Each agent catches per-item errors and marks individual items as needing review rather than propagating failures upward. The orchestrator's `finally` block always releases the job lock, even on unhandled exceptions.

### Real-Time Canvas UX

Rendering dozens of content cards on an infinite canvas with live Firestore updates pushed the frontend architecture hard.

Drag tracking uses React refs instead of state to avoid re-rendering the entire canvas on every mouse move. Coordinate transforms between screen space and canvas space (accounting for pan offset and zoom level) had to be pixel-perfect — off-by-one errors in transform math cause cards to "jump" when grabbed.

Live content streaming was the final piece. As the backend pipeline generates content, Firestore `onSnapshot` listeners push new docs into the canvas in real time. The spatial layout algorithm assigns positions to incoming cards without overlapping existing ones, while the user might be simultaneously dragging cards to new positions. Reconciling server-pushed layout with user-driven layout required careful conflict resolution.

## Accomplishments that we're proud of

**A full multi-agent pipeline that actually ships.** Not a demo with hardcoded outputs — the orchestrator runs Planner, Generator, Compliance, and Asset Manager in sequence under a real timeout budget, with graceful degradation at every stage. Every path produces usable content.

**Compliance that self-heals.** The evaluator-optimizer loop catches brand violations and regenerates content with targeted feedback — no human in the loop. Items below $s = 80$ get specific violation details and suggested fixes injected back into the prompt, improving on each retry.

**Real-time pipeline visibility.** The user sees progress update live as each stage completes — not a spinner with "please wait." Firestore `onSnapshot` streams job status and content docs to the frontend the moment they're written, so cards appear on the canvas as the pipeline produces them.

**An infinite canvas that feels native.** Pan, zoom, multi-select, drag, and SVG connection lines at 60fps — with new content streaming in from the backend without disrupting the user's spatial arrangement.

**Zero client-side API keys.** The Gemini API key lives exclusively in Cloud Functions via `defineSecret`. The frontend never sees it, even during development.

## What we learned

**Deterministic orchestration beats LLM routing.** We considered having an LLM decide which agent to call next. Pure code control turned out to be faster, cheaper, more debuggable, and more predictable. The pipeline is a fixed sequence — the interesting decisions happen inside each agent, not between them.

**Minimal agent context is critical.** The Planner assembles only the fields each downstream agent needs — product name, brand, features, compliance rule text. Passing full Firestore documents would waste tokens and confuse the model. Combinations are capped at 6 to keep generation time bounded.

**The evaluator-optimizer pattern works.** Separating compliance evaluation from content generation (rather than asking the generator to self-evaluate) produces more honest scores and more targeted feedback. The generator improves measurably when given specific violation details and suggested fixes.

**Firestore is an excellent real-time state bus.** Using `onSnapshot` subscriptions for both job progress and content delivery eliminated the need for WebSocket infrastructure. The frontend doesn't poll — it reacts to Firestore writes as they happen, making the pipeline feel responsive even though the backend is doing heavy LLM work.
